# OptiFlow

**Multi-tenant SaaS for managing machine downtime in manufacturing plants.**

When a workstation stops, OptiFlow drives the incident from detection all the way to a
validated return to production — and turns every timestamp collected along the way into
plant KPIs.

Each plant / organization is a **tenant**, with strictly isolated data.

---

## The downtime lifecycle

```
  ┌───────────┐   ┌────────┐   ┌─────────────┐   ┌───────┐   ┌──────────────────┐
  │ Detection │──▶│ Notify │──▶│ Acknowledge │──▶│ Track │──▶│ Resolve+validate │
  └───────────┘   └────────┘   └─────────────┘   └───────┘   └──────────────────┘
        │              │              │              │                │
        └──────────────┴──────────────┴──────────────┴────────────────┘
                                      ▼
                                    KPIs
```

1. **Detection** — a workstation stops; a downtime **ticket** is opened.
2. **Notify** — the responders responsible for that station are alerted.
3. **Acknowledge** — a responder takes the ticket; the response clock starts.
4. **Track** — responders keep the ticket current (status, cause, actions) through
   diagnosis and repair.
5. **Resolve & validate** — the fix is applied and production is validated back to normal.
   Only then is the ticket closed.
6. **KPI feed** — every event and timestamp feeds the plant's metrics (MTTR, MTBF, downtime
   duration, availability, SLA adherence, breakdowns by cause / line / shift / station).

## Glossary

| Term | Meaning |
|---|---|
| **Tenant** | A plant / organization using OptiFlow. All data is scoped to it. |
| **Responder** | A human technician who acknowledges and resolves downtime tickets. |
| **Workstation** | The monitored production asset that can go down. |
| **Downtime ticket** | The tracked incident record, from detection to validated resolution. |
| **UAP / Production line** | The plant's organizational units above a workstation. |

```
backend/    FastAPI + Firestore service     → backend/README.md
frontend/   React web app (plant managers)  → frontend/README.md
mobile/     React Native app (responders)   → mobile/README.md
.claude/    Development tooling & conventions
```

| Surface | Stack | Who uses it |
|---|---|---|
| **backend** | FastAPI · Firestore · Pub/Sub · Cloud Tasks · Cloud Run · Pydantic | — |
| **frontend** | React · TypeScript · TailwindCSS · Zustand · Vite | Plant managers: configuration, dashboards, KPIs |
| **mobile** | React Native (Expo) · TypeScript · NativeWind · Zustand | Responders on the shop floor: declare, acknowledge, resolve |

Firestore is schemaless — there is **no relational ORM and no migrations**. Pub/Sub and
Cloud Tasks drive downtime notifications and workflow steps: an endpoint *publishes*, it
never runs the job in-process.

## Getting started

### Backend

```bash
cd backend
python3 -m venv .venv                          # first time only
.venv/bin/pip install -r requirements-dev.txt  # runtime + test dependencies
cp .env.example .env                           # then fill in the values
.venv/bin/python -m pytest -q                  # run the suite
.venv/bin/uvicorn src.app.main:app --reload    # http://localhost:8000
```

Always run through the venv's interpreter — a bare `pytest` may resolve to a system install
and fail with a `ModuleNotFoundError` that looks like a missing dependency.

Requires Google Cloud credentials: point `GOOGLE_APPLICATION_CREDENTIALS` at a service
account key, or use Application Default Credentials.

### Frontend

```bash
cd frontend
npm install
npm run dev          # http://localhost:5173
```

Set `VITE_API_URL` to point at the backend (defaults to `http://localhost:8000`).

### Mobile

```bash
cd mobile
npm install
npx expo start
```

Set `EXPO_PUBLIC_API_URL` in `mobile/.env`. `app.json` is the **single source of truth** for
the native config — `android/` and `ios/` are generated by `expo prebuild` / EAS Build and
are deliberately not checked in. Never edit generated native files directly.

## Conventions

Coding conventions live in `.claude/skills/` — one per layer (`api`, `async`, `test`,
`doc`, `review`, `frontend`, `mobile`). They are the reference for where code goes and what
the quality bar is, whoever is writing it. The key ones:

- **Backend** — one folder per resource under `src/app/routers/`, each with its endpoints,
  input/output models and services. Background handlers live in `src/app/async_jobs/` and
  are registered in its dispatch table.
- **Frontend / mobile** — components stay small and presentational; fetching and logic live
  in a Zustand store or a pure util, never in a component. Store shapes mirror the backend
  `ApiResponse` contract exactly, and the web and mobile stores for the same resource share
  that shape.
- **Async** — the endpoint publishes to Pub/Sub or Cloud Tasks; it never dispatches
  in-process.

`CLAUDE.md` and `.claude/ORCHESTRATOR.md` describe how work is planned and split before it
gets written.
